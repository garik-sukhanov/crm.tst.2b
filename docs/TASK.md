# Техническое задание

Исходный текст задания. По нему сверяемся на каждом этапе (см. [PLAN.md](PLAN.md)).

## 2. Функциональные требования

В системе две роли, объекты и задачи по объектам с циклом статусов и историей изменений.

### 2.1. Роли

| Роль        | Что может                                                                                                                       |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Постановщик | создаёт, редактирует и удаляет объекты и задачи; назначает исполнителя; принимает задачи или возвращает на доработку; видит всё |
| Исполнитель | видит только свои задачи и объекты, в которых у него есть задачи; берёт задачу в работу и отправляет на проверку                |

Постановщиков и исполнителей может быть несколько.

### 2.2. Объекты

Объект — это стройка. Поля: название, адрес. В карточке объекта — список его задач со статусами.

### 2.3. Задачи

Поля: название, описание, объект, исполнитель, статус, автор, дата создания.

Статусы и переходы:

| Из статуса   | В статус     | Кто может               | Условие                |
| ------------ | ------------ | ----------------------- | ---------------------- |
| —            | Новая        | постановщик             | при создании задачи    |
| Новая        | В работе     | назначенный исполнитель | —                      |
| В работе     | На проверке  | назначенный исполнитель | —                      |
| На проверке  | Принята      | постановщик             | —                      |
| На проверке  | На доработке | постановщик             | комментарий обязателен |
| На доработке | В работе     | назначенный исполнитель | —                      |

Другие переходы запрещены.

### 2.4. История задачи

Каждая смена статуса сохраняется: кто, когда, из какого статуса в какой, комментарий (если есть). История видна в карточке задачи обеим ролям.

### 2.5. Экраны

- Вход по email и паролю.
- Список объектов.
- Карточка объекта со списком задач.
- Карточка задачи: данные, кнопки доступных действий, история.
- «Мои задачи» для исполнителя.

Интерфейс показывает только те действия, которые доступны текущему пользователю в текущем статусе задачи.

## 3. Требования к безопасности

Безопасность — обязательная часть задания: в наших проектах реальные данные клиентов. Правила доступа должны работать, даже если обращаться к Supabase напрямую, в обход интерфейса.

- Права доступа закрыты на уровне базы (RLS), а не только скрыты в интерфейсе.
- Исполнитель не может прочитать или изменить чужие задачи.
- Переходы статусов проверяются на стороне базы: запрещённый переход не пройдёт, даже если отправить запрос вручную.
- Историю статусов нельзя подделать, изменить или удалить через API.
- Открытая регистрация отключена. Тестовых пользователей можно создать вручную в Supabase.
- Секретные ключи (service_role и подобные) не попадают во фронтенд и в репозиторий.

## 4. Что сдать

В сдаче четыре вещи, одним сообщением в чат по отклику на hh.ru.

1. Ссылка на работающее приложение (Vercel, Netlify, свой сервер — не важно) и доступы: минимум один постановщик и два исполнителя. В базе — 2–3 объекта и несколько задач в разных статусах.
2. Репозиторий на GitHub (открытый или с доступом для нас) с миграциями базы и коротким README: как запустить проект.
3. Объяснение для руководителя-непрограммиста: видео до 5 минут или текст на полстраницы. Как устроена система, как защищены данные и что не может сделать исполнитель. Без терминов или с объяснением терминов.
4. Список решений и допущений: что вы решили сами там, где ТЗ не даёт однозначного ответа, и что не успели.
