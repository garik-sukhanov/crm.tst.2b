# Стройки — задачи по объектам

Постановщик заводит объекты (стройки) и задачи, исполнитель берёт их в работу и сдаёт на проверку. У каждой задачи своя история смены статусов и переписка. Все правила доступа проверяет база данных, а не только интерфейс.

## Сценарии для проверки

Номера задач — как в исходных данных. Если сценарий уже прогоняли, статусы могут отличаться.

**1. Постановщик проверяет работу** — `manager@stroy.example`

1. Объекты → «ЖК „Северный“, корпус 2». Это доска с колонками статусов.
2. Т-002 «Монтаж опалубки лестничного марша» лежит в колонке «На проверке». У неё две кнопки: «Принять» и «Вернуть на доработку».
3. Перетащите карточку в колонку «На доработке» или нажмите кнопку. Откроется окно: без комментария вернуть нельзя.
4. Откройте задачу. В ленте видно, кто, когда и из какого статуса в какой её перевёл, вместе с комментарием.

**2. Постановщик ведёт объекты и задачи** — `manager@stroy.example`

1. Объекты → «Новый объект»: название и адрес.
2. На доске объекта → «Задача»: название, описание, исполнитель. Задача появится в колонке «Новая».
3. В карточке задачи доступны «Изменить» и «Удалить», в меню «⋯» на доске — изменение и удаление объекта.

**3. Исполнитель делает задачу** — `kovalev@stroy.example`

1. После входа открываются «Мои задачи» по всем объектам.
2. Т-006 «Монтаж секционных ворот» → «Взять в работу» → «На проверку».
3. Других действий у исполнителя нет: принять задачу, создать или изменить её он не может.
4. Напишите сообщение в ленте задачи — его увидит постановщик.

**4. Исполнитель исправляет замечание** — `orlov@stroy.example`

1. Т-003 «Гидроизоляция приямков» в статусе «На доработке». В ленте — комментарий постановщика, что исправить.
2. «Взять в работу» → «На проверку».

**5. Исполнитель не видит чужого** — `kovalev@stroy.example`

1. В «Объектах» нет «Частного дома в Митино»: там нет его задач.
2. На доске «ЖК „Северный“» видны только его задачи. Задачи Орлова (Т-003, Т-004) не показываются.
3. Откройте по прямой ссылке задачу Орлова: `/tasks/bbbbbbbb-0000-4000-8000-000000000003`. Ответ — «Задача не найдена». Этот отказ даёт база, а не интерфейс.

**6. Статистика (сверх задания)** — любой пользователь

1. Статистика: открытые задачи, ожидают проверки, доля возвратов, среднее время до приёмки, разбивка по объектам и исполнителям, приёмки и возвраты за 14 дней.
2. Исполнитель видит её только по своим задачам.

**7. Телефон и темы**

1. На ширине телефона навигация переезжает в нижнюю панель, а доска превращается в табы статусов с кнопками действий.
2. Тема переключается в шапке: светлая, тёмная или как в системе.

## Запуск локально

Нужны Node 22+, pnpm 10 и Docker.

```bash
pnpm install
```

```bash
pnpm db:start
```

```bash
pnpm dev:local
```

Откройте http://localhost:5180. `db:start` поднимает Supabase в Docker и применяет миграции и сид. `dev:local` запускает приложение против локальной базы. Адрес и публичный ключ лежат в `.env.localdb`: это стандартные демо-значения Supabase CLI, их можно сверить с `pnpm supabase status`.

Сбросить базу к исходным данным:

```bash
pnpm db:reset
```

## Облачный Supabase

```bash
pnpm supabase login
```

```bash
pnpm supabase link --project-ref <project-ref>
```

```bash
pnpm supabase db push --include-seed
```

```bash
pnpm supabase config push
```

Последняя команда переносит настройки авторизации из `supabase/config.toml`, в том числе выключенную регистрацию. Перед ней поменяйте `site_url` на адрес приложения. Можно и вручную: Authentication → Sign In / Providers → снять «Allow new users to sign up».

Фронтенду нужны только публичные значения: скопируйте [.env.example](.env.example) в `.env.local` и заполните. Секретный ключ (`service_role` / `sb_secret_…`) во фронтенд и в репозиторий не попадает.

## Деплой на Netlify

Сайт https://crm-stroy-tasks.netlify.app подключён к этому репозиторию: каждый push в `main` выкладывается сам, для pull request Netlify собирает превью. Настройки сборки, переходы для SPA и заголовки безопасности лежат в [netlify.toml](netlify.toml). Переменные `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` заданы в Netlify → Site configuration → Environment variables.

Для своего сайта: Netlify → Add new site → Import an existing project → GitHub → этот репозиторий. Задайте те же две переменные, а в Supabase укажите адрес сайта: Authentication → URL Configuration → Site URL.

## Деплой на Vercel (альтернатива)

Подключите репозиторий и задайте переменные окружения `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`. Остальное — сборка, переходы для SPA, заголовки безопасности — описано в [vercel.json](vercel.json).

## Проверки

| Команда                 | Что проверяет                                                           |
| ----------------------- | ----------------------------------------------------------------------- |
| `pnpm verify`           | Biome, границы слоёв FSD (Steiger), TypeScript, unit-тесты              |
| `pnpm test`             | Unit-тесты: правила переходов, модели Effector, расчёт статистики       |
| `pnpm test:db`          | pgTAP: права прямо в базе — видимость, переходы, неизменяемость истории |
| `pnpm test:integration` | Те же правила через публичный API с настоящим входом по паролю          |

GitHub Actions ([.github/workflows/ci.yml](.github/workflows/ci.yml)) запускает всё это на каждый push. Для тестов базы поднимается Supabase в Docker.

## Где что лежит

```
supabase/
  migrations/      схема и правила безопасности
  seed.sql         тестовые данные
  tests/database/  pgTAP
src/
  app/             запуск, маршруты, стили и темы
  pages/           экраны: вход, объекты, доска, задача, мои задачи, статистика
  widgets/         каркас, доска задач, лента задачи
  features/        вход/выход, смена статуса, чат, редакторы объектов и задач, тема
  entities/        пользователь, объект, задача (API, правила переходов, карточки)
  shared/          клиент Supabase, UI-кит, утилиты
tests/integration/ проверки через API
```
